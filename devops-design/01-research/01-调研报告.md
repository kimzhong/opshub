> 场景：金融/制造类企业，**公有云 + 私有云混合**，技术栈不统一，从零规范
> 目标交付：真实生产平台设计 + 本地 `kind` 多集群可运行骨架

## 0. 摘要（TL;DR）

调研覆盖 11 个关键技术域。结合场景约束（金融/制造混合云 + 零基础规范化 + 真实生产），核心选型建议：

| 域 | 推荐 | 备选 | 关键理由 |
|---|---|---|---|
| **容器编排** | Kubernetes（自管）+ 多发行版可选 | Rancher / Cluster API | K8s 已是行业唯一标准；混合云要靠 Cluster API 统一供给 |
| **GitOps** | **ArgoCD** + ApplicationSet | Flux v2 | UI 对运维/审计友好；ApplicationSet 是多集群 GitOps 事实标准 |
| **CI** | **GitHub Actions（构建层）** + **Argo Workflows（流水线编排）** | Tekton | GitHub Actions 拉新最快；Argo Workflows 适合长时/容器化流水线 |
| **镜像仓库** | **Harbor**（自管） + Cosign 签名 | ACR / ECR | 等保/数据驻留要求；Cosign 是 SLSA L3 必需 |
| **IaC** | **Terraform/OpenTofu**（基础资源） + **Crossplane**（应用自服务） | Pulumi | Terraform 生态最广；Crossplane 给开发者自助、零状态文件 |
| **多集群网络** | **Submariner**（CNI 中立） 或 **Cilium ClusterMesh**（如果全用 Cilium） | Istio Multicluster | 混合云跨 CNI 场景 Submariner 优势明显 |
| **服务网格** | **Istio**（生产级） | Linkerd / Cilium | 多语言 mTLS、流量管理成熟；Ambison 模式减 sidecar 开销 |
| **IAM** | **Keycloak**（中心 IdP） + **Dex**（K8s API 代理） | Ory Hydra | 唯一支持多集群 OIDC + 用户联邦的成熟开源组合 |
| **可观测** | **LGTM + Mimir**（Prometheus + Grafana + Loki + Tempo + Mimir） + OpenTelemetry | Datadog / New Relic | 自主可控、成本可预测；OTel 是厂商中立标准 |
| **告警** | **Alertmanager** + 多窗口 Burn Rate + PagerDuty/Opsgenie | Grafana Alerts | 业界 SRE 标准；Burn Rate 比静态阈值噪声低 90% |
| **灾备** | **Velero**（应用级） + **etcd 快照**（控制面） + **Restic/Kopia**（PV 数据） | Kasten | 跨云跨集群一致备份；Restic 处理非 CSI 卷 |
| **混沌工程** | **Chaos Mesh**（细粒度） + **LitmusChaos**（多步实验） | Gremlin | 两开源 CNCF 项目覆盖 Pod/Node/Network/IO/Time/DNS 全故障类型 |
| **镜像签名** | **Cosign + Kyverno**（强制签名准入） | Notary v2 | Sigstore 是 CNCF 标准；Kyverno 策略写起来比 OPA 友好 |

**选型哲学**：能选 CNCF Graduated 不选 Incubating；能选生态最广不选最快；自建只建"gap filler"——这一点在 2026-08 用户的实际反馈中已经明确过：自研通用组件是浪费。

## 1. 场景画像与目标

### 1.1 业务场景

- **行业类型**：金融 / 制造（合规要求高、稳定性要求高、容灾要求高）
- **云环境**：公有云（业务/弹性）+ 私有云/IDC（核心数据/合规），混合架构
- **现状**：技术栈不统一，需要"从零规范"——意味着设计时要"想清楚再推广"，且平台必须有足够的弹性承接不同业务线的需求
- **组织**：假设有 SRE 平台团队（5-15 人）+ 业务研发团队（50-500 人）

### 1.2 设计目标

1. **可解释**：架构、选型、流程必须有文档可查、可讲解
2. **可执行**：本地 `kind` 跑得起来，每一步都有可运行脚本
3. **可演进**：从单集群 demo 演进到多集群/多云/合规生产
4. **可治理**：权限、审计、策略、镜像签名、SLO 一应俱全

### 1.3 非目标

- 不做完整端到端业务应用（只做平台 + 一个示范应用）
- 不替代公司现有自研系统（如已有 CMDB、工单系统）
- 不在 `kind` 本地模拟多云（设计上覆盖，实跑只能单 cloud）

## 2. 行业现状（2026）

### 2.1 关键趋势

1. **GitOps 已成 K8s 部署默认范式**。CNCF 2026 报告显示 78% 的 K8s 用户采用 GitOps；MTTR 比传统 push 模式低 40-60%、变更失败率从 15% 降到 5% 以内
2. **多集群 K8s 进入"去联邦化"阶段**。KubeFed v1/v2 已废弃（2023 归档）；当前主流是 `Cluster API` 供给 + `ArgoCD ApplicationSet` / `Flux` GitOps 分发，Karmada 仍存在但定位特殊场景
3. **可观测三大支柱 + OpenTelemetry 标准**。Prometheus + Grafana + Loki + Tempo/Mimir + OpenTelemetry 几乎成为开源事实标准；Datadog 等 SaaS 仍在大型企业渗透
4. **IaC 工具三分天下**。Terraform（计划/应用模式 + 最大生态）+ Pulumi（编程语言）+ Crossplane（K8s 原生持续协调）；OpenTofu 是 Terraform 的开源分叉
5. **供应链安全合规化**。SLSA Framework L3、Cosign/Sigstore 签名、Syft SBOM、Kyverno/OPA 准入成为金融/制造标配
6. **混沌工程走出"破坏"误区**。从"随机搞坏生产"转向"基于 SLO 的持续验证"，Litmus/Chaos Mesh 几乎所有 SRE 成熟团队的标配

### 2.2 反模式（要避开的坑）

- ❌ 自研 GitOps 引擎（JSM/AAP/Bitbucket 已有轮子）
- ❌ "All-in-one" 监控平台采购（成本锁死 + 数据出域）
- ❌ 单集群跨云拉 etcd（延迟会咬人）
- ❌ 共享 kubeconfig 跨集群（凭证轮转是灾难）
- ❌ 在没有 SLO 的情况下做混沌工程（盲人摸象）
- ❌ 静态阈值告警（PagerDuty 数据显示这类告警 70% 无需响应）
- ❌ "kubectl apply 到生产" + 偶尔的 GitOps 混用（drift 不可见）

## 3. 关键技术域调研

### 3.1 GitOps：ArgoCD vs Flux

**结论**：选 **ArgoCD**（含 ApplicationSet 和 Notifications 子项目）。

| 维度 | ArgoCD | Flux v2 |
|---|---|---|
| 成熟度 | CNCF Graduated（2022-12） | CNCF Graduated（2022-11） |
| 架构 | 单体服务（API+UI+Controller+Redis） | 控制器矩阵（source/kustomize/helm/notification/image-automation） |
| UI | 内置强大 Web UI | 无（需 Weave GitOps 或自建） |
| 多集群 | ApplicationSet 跨集群模板 | 借助 Cluster API bootstrap |
| 多租户 | 内置 Project + RBAC（Casbin） | 依赖 K8s 原生 RBAC |
| 镜像自动更新 | 需外部 CI 改 manifest | 内置 image-automation-controller |
| Terraform | 需外部 runner（Atlantis） | 配 tf-controller 可真 GitOps |
| Git 不可达 | App 标 OutOfSync，停止同步 | 保留 last-known-good 继续对账 |
| 资源占用 | 重（API/UI/Redis） | 轻（独立控制器） |
| 社区 | 17.8k stars，生态最大 | 6.5k stars，企业采用少于 ArgoCD |

**为什么 ArgoCD**：
- Web UI 是金融/制造环境下审计/演示的关键卖点
- ApplicationSet 是多集群 GitOps 事实标准
- Notifications 子项目把告警/通知做进 GitOps 闭环
- 用户案例（Stripe、BlackRock、Ant Group）已验证金融场景

**注意**：Flux 优势在"更轻、更 K8s 原生、自动镜像更新"。如果团队能接受"无 UI + CLI/CRD 工作流"，Flux 也是合理选择。**OpsHub 选 ArgoCD，但保留 Flux 作为备选**——通过 `App of Apps` 模式可以无痛切换。

### 3.2 CI/CD：GitHub Actions + Argo Workflows

**结论**：**双层架构**——GitHub Actions 做构建/单测/SCA 扫描；Argo Workflows 做多语言、多步骤、容器化流水线（如：构建 → 扫描 → 签名 → 多环境部署）。

**为什么不是单一工具**：
- Jenkins → 维护成本高、插件治理差，金融场景下还常见审计问题
- Tekton → 学习曲线陡，但非常适合"想用 K8s 本身做 CI 引擎"的团队
- GitLab CI → 绑定代码托管，如果代码已经在 GitHub/自建 Gitea，迁移成本高
- GitHub Actions → 默认起点，70% 新项目首选；Marketplace 20000+ actions

**典型分层**：
```
开发者 push → GitHub Actions 触发
  ├─ Lint、Unit Test、SAST
  ├─ Container Build（BuildKit）
  ├─ Trivy 扫描 + Cosign 签名
  └─ 推送镜像到 Harbor + 更新 GitOps repo
       └─ ArgoCD 检测到 commit → Argo Workflows 跑多环境 promotion
            ├─ canary
            ├─ 自动化测试
            └─ full rollout
```

**Tekton vs Argo Workflows**：
- Tekton 更"CI 范式"（Task → Pipeline → PipelineRun）
- Argo Workflows 更"通用 DAG 编排"（DAG with retry/timeout/suspend）
- 都有 CNCF 支持；如果未来要做"CI/CD 全 K8s 内自闭环"，Tekton 更纯粹
- 选 Argo Workflows 的现实理由：和 ArgoCD 同生态、配置更直观、社区案例多

### 3.3 IaC：Terraform/OpenTofu + Crossplane

**结论**：**两层架构**——Terraform 管云资源（VPC/RDS/ACK 等），Crossplane 给应用团队做"自服务"（如：自助申请 Postgres、Redis）。

| 工具 | 范式 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| Terraform/OpenTofu | Plan/Apply + 状态文件 | 生态最大（3500+ provider） | 状态管理痛苦，无自动对账 | 基础资源 |
| Pulumi | 真实编程语言（Go/TS/Python） | 强抽象、强类型、IDE 友好 | 生态依赖 bridge 转换 | 复杂逻辑 |
| Crossplane | K8s 控制器持续对账 | 零状态文件、原生 GitOps、CRD 自服务 | 学习曲线陡、需 K8s 集群 | 应用自服务 |

**为什么这么选**：
- Terraform 仍是基础资源的事实标准；OpenTofu 是它的开源分叉（License 友好的备份）
- Crossplane 在 K8s 团队里越来越被推荐（"Kubernetes-native IaC"）——给业务团队一个 `Postgres` Claim，无需关心 RDS 还是自管
- 金融场景对"审计/合规"要求高：Crossplane 的"所有资源都是 K8s 资源"特性天然契合 GitOps 审计

**反模式**：纯 Crossplane 管云上基础网络（VPC 路由表等）——风险大、跨集群难；Terraform 管应用级 RDS 之类的"频繁变更资源"——状态文件易冲突。

### 3.4 多集群 K8s 拓扑

**结论**：**Hub-Spoke + GitOps 驱动**，不引入 meta-control-plane。

**为什么 KubeFed 不可用**：
- KubeFed v1/v2 已归档（2023-04），SIG Multicluster 弃坑
- Karmada 是其精神继承者（CNCF Incubating），Bloomberg/Huawei 在用，但仍是"特殊场景"工具

**主流模式（2026）**：
```
        ┌─ mgmt cluster（ArgoCD/ArgoWF/监控/IAM）
        │  └─ 通过 Cluster API 供给 workload cluster
        │
   ┌────▼────┬────────┬────────┐
   │ spoke-1 │ spoke-2│ spoke-3 │  ← 各自独立 etcd、独立生命周期
   └─────────┴────────┴────────┘
```
- 每个 spoke 集群**独立可销毁**（"cattle, not pets"）
- ArgoCD 在 mgmt 集群运行，通过 `cluster registry` 管理所有 spoke
- 跨集群流量：Submariner 隧道 或 ClusterMesh
- 镜像分发：Harbor Replication（region 内 + 跨 region）

**Cluster API 的角色**：
- 不直接做"多集群编排"，而是"声明式供给集群"
- 强烈推荐在 `kind` 模拟生产时使用，让供给侧也可视化

### 3.5 混合云多集群网络

**结论**：**Submariner**（CNI 中立）；如果决定全栈用 Cilium 则选 **Cilium ClusterMesh**。

| 工具 | 跨集群延迟（同 region）| 跨 region | CNI 要求 | 资源占用 | 加密 |
|---|---|---|---|---|---|
| Submariner 0.19 | 8ms | 45ms | 任意 | 中（hub-spoke） | IPSec/WireGuard |
| Cilium ClusterMesh 1.16 | 6ms | 42ms | 仅 Cilium | 中（full-mesh） | WireGuard/IPSec |
| Istio Multicluster | 14ms | 58ms | 任意 | 高（sidecar/ambient） | mTLS L7 |

**关键决策点**：
- 混合云意味着**不同云厂商 + 私有 IDC**，CNI 难以统一（公有云常用云厂商 CNI，IDC 用 Cilium/Calico）。Submariner 的"任意 CNI"是决定性优势
- 跨集群延迟都是 10-50ms 级别，**强烈不推荐**做同步调用（"两集群同应用"做读写不分离）
- 私有 IDC 跨公网需要**专线/SD-WAN + WireGuard/IPSec**——Submariner 已有内置

**网络规划硬规则**（来自业界经验）：
- ❌ 不要在两个集群用相同 Pod CIDR（默认 10.244.0.0/16 极易冲突）
- ❌ 不要"为所有端口开防火墙"（要白名单最小化）
- ❌ 不要让 DNS TTL 继承通用值（要 30-60s）
- ✅ 必须做 Path MTU 测量（隧道封装会降低 MTU）
- ✅ 跨集群依赖必须有中央 registry 记录

### 3.6 镜像仓库与供应链安全

**结论**：**Harbor**（自管）+ **Cosign** 签名 + **Kyverno** 强制准入。

**为什么是 Harbor**：
- CNCF Graduated，自管可选
- 内置 Trivy 扫描（不用单独搭 scanner）
- 支持签名（Cosign + Notary v2）
- 项目级 RBAC（"dev" 和 "prod" 项目隔离）
- 复制策略成熟（基于 P2P 拉模式，不烧公网带宽）
- 替代品：AWS ECR / Azure ACR / Harbor 各自组合；金融场景多云需要 Harbor

**Cosign + Kyverno 工作流**：
```
[ CI 构建镜像 ] → [ Trivy 扫描 ] → [ Cosign 签名 ] → [ Push 到 Harbor ]
                                                                │
[ K8s 部署请求 ] → [ Kyverno Verify ] ← 验签 ← ────────────────┘
                         │
                         ├─ 通过 → 准入 → Pod 启动
                         └─ 失败 → 拒绝 → 审计日志
```

**额外保障**：
- **SLSA L3 Provenance**：用 `actions/attest-build-provenance` 或 Tekton Chains 生成构建来源证明
- **SBOM**：用 Syft 生成 SPDX 格式，附在镜像旁
- **准入策略**：Kyverno 写 `verifyImages` 比 OPA Gatekeeper 简单（不需要学 Rego）

### 3.7 IAM：Keycloak + Dex 联合

**结论**：**Keycloak** 作中心 IdP，**Dex** 作 K8s API 的 OIDC 代理层。

**为什么需要 Dex**（而不是 K8s API 直连 Keycloak）：
- 多个 K8s 集群的 API Server 都挂同一个 issuer 容易配置不一致
- Keycloak 已对接 AD/LDAP/GitHub，Dex 可以把这些 IdP 的用户再"包装"成 K8s 认识的 OIDC
- Dex 缓存 + 短 token（15-30min）让集群更安全

**典型架构**：
```
用户登录
  │
  ▼
Keycloak（中心 IdP，HA 部署，PG 后端）
  │ （OIDC）
  ▼
Dex（OIDC 代理 + IdP 联邦）
  │ （OIDC token，groups claim）
  ▼
K8s API Server（--oidc-* flags）
  │
  ▼
RBAC（ClusterRoleBinding 绑定到 groups）
```

**生产关键**：
- Keycloak **绝对不要**部署在它要认证的 K8s 集群里（雪崩风险）
- `--oidc-issuer-url` 必须用 HTTPS（自签 CA 要 `--oidc-ca-file`）
- Group Membership Mapper 在 Keycloak client 必须配（"groups" claim 不配 = 所有人没权限）
- `preferred_username` 映射到 `username`，别用 email（会变）

**多集群模式**：一个 Keycloak realm 服务所有集群，通过 group 后缀区分（`k8s-prod-admins` / `k8s-staging-admins`）。

### 3.8 可观测性栈：LGTM + Mimir

**结论**：**Prometheus + Grafana + Loki + Tempo + Mimir** + **OpenTelemetry**。

**为什么这套**（vs Datadog / New Relic）：
- 成本可控：Datadog 20 服务规模 $5-30k/月，开源方案 $500-2k/月 + 工程师时间
- 数据驻留：金融/制造必须本地
- 厂商中立：OTel 标准化，切换后端不改代码
- CNCF 生态最广

**组件角色**：

| 组件 | 职责 | 数据 |
|---|---|---|
| Prometheus | 指标采集与短期存储 | Time-series（15d 本地） |
| Mimir | 长期指标存储 | 横向扩展 Prometheus，>15d |
| Loki | 日志聚合 | 仅索引 labels，存储便宜 |
| Tempo | 分布式追踪 | OTLP / Jaeger 协议 |
| Grafana | 统一可视化与告警 | 不存数据 |
| OTel Collector | 采集代理、路由、采样 | 标准化管道 |
| Promtail / Vector / Fluent Bit | 日志采集 | Sidecar / DaemonSet |
| Alertmanager | 告警路由/抑制/静默 | 通知分发 |

**关键设计**：
- 所有应用 **用 OTel SDK 注入**（Go/Python/Node/Java），不直接用 vendor SDK
- 日志 shipper **不要在每个 Pod 装 Filebeat**——用 DaemonSet 节点级采集（成本/性能最优）
- 指标采集：kube-prometheus-stack 提供开箱即用的 K8s 监控
- **不要**在生产自建存储后端用 Loki 单体（磁盘爆炸）——用 Loki + S3/MinIO 长期存储

**eBPF 加分项**（可选）：
- Cilium Tetragon：运行时安全 + 网络可观测
- Pixie：自动应用层 eBPF 探针（开发环境很香，生产慎用开销）
- Hubble：Cilium 网络可视化

### 3.9 告警与 SRE 实践

**结论**：**SLO 驱动 + 多窗口 Burn Rate**（Google SRE Workbook 标准）。

**反模式（要避开的）**：
- ❌ 静态阈值（"CPU > 80%"）—— 70% 告警无响应
- ❌ 原因告警（"DB CPU 高"）而非症状告警（"下单 P99 > 3s"）
- ❌ 一次事故产生 20 个独立告警
- ❌ 告警没有 runbook 链接

**SLO 范例**：
```
服务：checkout-api
SLO：99.5% 请求 < 800ms（30 天滚动窗口）
Error Budget：0.5% = 216 分钟/月

Burn Rate 告警：
- 14.4x burn / 5min  → Page（1h 内耗光预算）
- 6x burn / 30min    → Page
- 1x burn / 6h       → Ticket
```

**告警路由**：
```
Alertmanager
  ├─ group by [alertname, service]     ← 一次事故一个告警
  ├─ group_wait 30s                    ← 等同类告警合并
  ├─ inhibit warning when critical     ← 抑制冗余
  ├─ critical → PagerDuty
  ├─ warning  → Slack + email
  └─ info     → dashboard only
```

**on-call 实践**：
- 一个工程师一班最多 2 个 page（健康指标）
- MTTD < 5 min
- 50% 时间应该是工程改进（不是 toil）
- Blameless postmortem 每次 P0/P1 必做
- 影子 on-call 2-4 周再独立上岗

### 3.10 灾备与备份

**结论**：**Velero**（应用级）+ **etcd 快照**（控制面）+ **Restic/Kopia**（PV 数据）+ **分层保留策略**。

**RPO/RTO 分层**：
| 业务等级 | RPO | RTO | 策略 |
|---|---|---|---|
| Tier 0（核心交易） | < 1min | < 5min | 跨 region active-active + 数据库同步复制 |
| Tier 1（关键业务） | < 15min | < 30min | 跨 region active-passive + 持续复制 |
| Tier 2（一般业务） | < 1h | < 4h | 跨 region backup-restore |
| Tier 3（开发测试） | < 24h | < 24h | 同 region 备份 |

**Velero 关键经验**：
- 必须用 Restic 或 CSI snapshot（**不要**只备份 etcd/PVC 元数据）
- 备份存到 S3 with **Object Lock（WORM）**——防勒索软件
- S3 **跨 region 复制**用 Replication Time Control (RTC) 15min SLA
- 月度 DR drill 必做（"DR 没演练 = 没有 DR"）
- Velero 测试恢复：在隔离 namespace 做 `--namespace-mappings` 验证

**etcd 备份**：
- 每日 etcd snapshot + 上传 S3
- 备份前做 defrag（提高恢复成功率）

### 3.11 混沌工程

**结论**：**Chaos Mesh**（细粒度故障）+ **LitmusChaos**（多步实验工作流）。

**为什么两者都选**：
- Chaos Mesh 在 K8s 内 CRD 细粒度故障（PodChaos/NetworkChaos/IOChaos/TimeChaos/DNSChaos）
- LitmusChaos 的 ChaosHub 社区实验丰富，Litmus Workflow 适合"先杀 Pod → 观察 5min → 杀节点"这种链式实验
- 两者都是 CNCF 项目

**三层实验模型**（业界标准）：
| 层 | 频率 | 工具 | 实验 |
|---|---|---|---|
| Tier 1：Pod | 每日/自动 | Chaos Mesh | kill pod, CPU stress |
| Tier 2：Node | 每周/自动 | Chaos Mesh | drain node, AZ node kill |
| Tier 3：Region | 季度/game day | Litmus | partition, region switch |

**安全护栏**：
- 必须有 **stop condition**（SLO 违规即停止）
- 必须**通知 on-call**（30 秒动作，避免把测试当事故）
- 永远不要在 primary production DB 上做 TimeChaos（"state-based faults 是最危险的"）

## 4. 风险清单与缓解

| 风险 | 等级 | 影响 | 缓解 |
|---|---|---|---|
| ArgoCD 单点故障 | 中 | CD 失能 | HA 部署（多副本 + Redis HA），Git 是事实源 |
| Harbor 容量爆 | 中 | 推送失败 | 自动 GC 策略、保留 N 个 tag 规则 |
| Prometheus 长期存储成本 | 高 | 监控失明 | Mimir + 远程存储（Object storage） |
| Velero 恢复未演练 | 高 | 灾备失效 | 每月 DR drill + 监控 Velero 备份状态 |
| 跨 region 网络抖动 | 中 | 集群不可达 | 多 Submariner gateway + 健康检查 + 快速 failback |
| Keycloak 单点 | 高 | 全员无法登录 | HA + 离线 break-glass 凭证 |
| 镜像签名跳过 | 高 | 供应链被攻破 | Kyverno 强制准入（不做签名=不起 Pod） |
| 混沌实验失控 | 中 | 真实事故 | 必设 stop condition + on-call 通知 |
| SLO 未定义 | 高 | 告警失明 | 强制 P0 服务上线前必须有 SLO YAML |
| 多集群 CIDR 冲突 | 中 | 跨集群流量失败 | 创建集群前规划好 CIDR；用 Submariner Globalnet 兜底 |
