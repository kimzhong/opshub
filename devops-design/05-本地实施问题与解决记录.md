## 3. 真实问题与解决（5 个 bug）

### Bug 1：kubectl 1.30+ 移除 `--short` flag

**现象**：
```
[FAIL] kubectl not installed
[FAIL] Pre-flight failed
```

**诊断**：
- `kubectl version --client --short` 报 `error: unknown flag: --short`
- kubectl 1.30 已废弃 `--short`，必须用 `kubectl version --client`（无 `--short`）
- 之前的 `kind version` 也用了相同 try/catch 模式，但 kind 0.24 还支持短输出

**修复**（`create-clusters.ps1`）：

```powershell
# Before
$kubectlVersion = & kubectl version --client --short 2>&1

# After
$kubectlFull = & kubectl version --client 2>&1 | Out-String
$ver = ($kubectlFull -split "`n" | Select-String -Pattern 'Client Version' | Select-Object -First 1) -replace '.*v(\d+\.\d+\.\d+).*', '$1'
```

**教训**：kubectl 1.30+ 已废弃多个便利 flag（`--short`、`-o yaml` 部分字段），脚本需主动升级。

---

### Bug 2：kind v0.24 + K8s 1.30 移除 `node-role.kubernetes.io/control-plane` kubelet label

**现象**：
```
kubelet: failed to validate kubelet flags: unknown 'kubernetes.io' or 'k8s.io' labels 
specified with --node-labels: [node-role.kubernetes.io/control-plane]
--node-labels in the 'kubernetes.io' namespace must begin with an allowed prefix (...)
kubelet.service: Main process exited, code=exited, status=1/FAILURE
```

`kubectl get nodes` 返回 `EOF`（API server 未就绪，因为 kubelet 一直重启）。

**诊断**：
- K8s 1.30+ 收紧了 kubelet 启动 label 校验，移除了 `node-role.kubernetes.io/control-plane` 的白名单
- 应该用 `node.kubernetes.io/role=control-plane` 或者让 kind 自动加
- `ops-mgmt.yaml` 第 37 行手写了 `node-role.kubernetes.io/control-plane=` label 触发了这个校验

**修复**（`ops-mgmt.yaml`）：

```yaml
# Before
node-labels: "ingress-ready=true,node-role.kubernetes.io/control-plane="

# After
node-labels: "ingress-ready=true"
```

**教训**：kind 集群配置里**不应该手写** `node-role.kubernetes.io/control-plane`，kind + kubeadm 会自动设置。手写反而会被 K8s 拒绝。

### Bug 3：K8s 1.30 移除 `GatewayAPI` feature gate

**现象**：
```
kubelet: failed to set feature gates from initial flags-based config: 
unrecognized feature gate: GatewayAPI
kubelet.service: Main process exited
```

**诊断**：
- `ops-mgmt.yaml` 在 `featureGates` 块设了 `GatewayAPI: true`
- K8s 1.30 已将 GatewayAPI GA 化（不再需要 feature gate 开关）
- 任何带 `GatewayAPI` 字符串的 featureGates 配置都会失败

**修复**（`ops-mgmt.yaml`）：

```yaml
# Before
featureGates:
  "GatewayAPI": true

# After (注释掉，GA 默认开启)
# 注：K8s 1.30+ 已移除 GatewayAPI feature gate，GA 版本默认开启
# featureGates:
#   "GatewayAPI": true
```

**教训**：K8s 1.30 移除了多个 alpha feature gate（包括 ServerSideApply、BoundServiceAccountTokenVolume、GracefulNodeShutdown 等）。从 1.29→1.30 升级时，kind 集群配置里的 `featureGates` 块需要清理。

### Bug 4：PowerShell 5.1 NativeCommandError 让 create-clusters.ps1 中断

**现象**：
- 跑 `.\kind\create-clusters.ps1` 时，PS 进程几秒后退出
- log 显示 `kind.exe : Creating cluster "ops-mgmt" ...` 后报 `NativeCommandError`
- 但实际上 `kind get clusters` 显示集群创建成功（PowerShell 误报）

**诊断**：
- PowerShell 5.1 把 `kind` 写到 stderr 的任何内容（即使 stderr 是进度信息）当作 native command error
- 配合 `$ErrorActionPreference = 'Stop'`，脚本立即中断
- 但是 `& kind create cluster ... 2>&1 | Out-String` 把 stderr 重定向到 stdout，PS 还是会触发 NativeCommandError

**修复**（`create-clusters.ps1`）：

把 `& kind` 改成 `cmd /c 'kind ... & exit /b %errorlevel%'`，用 cmd.exe 间接调用绕过 PS 的 native command 解析：

```powershell
# Before
$output = & kind create cluster --config $configFile 2>&1 | Out-String
if ($LASTEXITCODE -eq 0) { ... }

# After
$output = cmd /c ('kind create cluster --config "' + $configFile + '" 2>&1 & exit /b %errorlevel%')
if ($LASTEXITCODE -eq 0) { ... }
```

同时加了"已存在则跳过"的保护（避免重复创建触发 `node(s) already exist`）：

```powershell
$existingOut = cmd /c 'kind get clusters 2>&1 & exit /b %errorlevel%'
$existingList = @()
if ($LASTEXITCODE -eq 0) {
    $existingList = $existingOut -split "`r?`n" | Where-Object { $_ -and $_.Trim() }
}
foreach ($c in $clusters) {
    if ($existingList -contains $c) {
        Write-Host ('  -> ' + $c + ' [SKIP] already exists') -ForegroundColor Yellow
        continue
    }
    ...
}
```

**教训**：PowerShell 5.1 + `$ErrorActionPreference='Stop'` + 任何写 stderr 的外部命令 = 必触发 NativeCommandError。**所有外部命令必须用 `cmd /c` 间接调用**。这是 PS5.1 + Windows 自动化脚本的根本限制，不是 bug。

### Bug 5：误杀 `com.docker.backend` 导致 Docker daemon 挂

**现象**：
- 在 ArgoCD 安装完成后做 port-forward 验证时，30443 端口不通
- 我用 `Get-NetTCPConnection -LocalPort 30443` 查占用进程，看到 PID 13464 (wslrelay) 和 PID 9724 (com.docker.backend)
- 我 `Stop-Process -Force` 杀了 PID 9724（以为是某个 port-forward 残留）
- 结果：Docker Desktop daemon 立刻挂掉，4 个 kind 集群的容器全部退出

**诊断**：
- `com.docker.backend` 是 Docker Desktop 的 **核心 service 进程**（管理 Docker daemon、networking、volume 等）
- 我误以为它是无害的 port-forward 进程
- 杀掉它等于杀掉 Docker 守护进程，所有 kind 容器立刻死掉

**未解决**（用户需手动操作）：
- Docker Desktop 进程在跑（4 个 `Docker Desktop.exe`），但 `com.docker.service` 卡在 Stopped
- 4 个 `Docker Desktop.exe` 进程属于 UI 渲染层，触发不了 service 重启
- `Restart-Service com.docker.service` 报 "无法打开服务"（service 已 down）
- `sc start com.docker.service` 报 "Access is denied"（需要 admin 权限）

**临时恢复**（用户操作）：
1. 打开任务管理器 → 结束所有 `Docker Desktop.exe` 进程（4 个）
2. 等待 5 秒
3. 双击桌面 `Docker Desktop` 快捷方式重新启动
4. 等待 Docker Desktop 完全就绪（系统托盘图标变绿，~60-90s）
5. 重跑 `kind create cluster --config clusters/ops-mgmt.yaml --wait 5m` 等 3 个集群
6. 重跑 `install-argocd.ps1` 部署 ArgoCD

**教训**：
- **不要 kill `com.docker.backend` 进程**（即使是"看起来无害"）
- 验证 port-forward 问题应该用 `Get-NetTCPConnection` + 看进程 `Path` 字段，不要凭 `ProcessName` 猜
- Docker Desktop 在 Windows 上有 4-5 个相互依赖的进程：UI、backend service、wslrelay、vpnkit-bridge，**任何一个挂掉都可能导致 daemon 失联**

## 8. 经验教训（5 条）

1. **PowerShell 5.1 + 任何写 stderr 的 CLI = 必踩 NativeCommandError**
   - 通用解法：所有外部命令用 `cmd /c '<cmd> 2>&1 & exit /b %errorlevel%'`
   - 在脚本入口处定义 `Invoke-External` 辅助函数统一封装

2. **K8s 1.30 是大版本变更**
   - `--short` flag 废弃、GatewayAPI GA、`node-role.kubernetes.io/control-plane` 校验收紧
   - kind v0.24 + K8s 1.30 是当前最稳组合（kind v0.23 拉 K8s 1.30 镜像也会有兼容问题）

3. **Docker Desktop 在 Windows 上是多进程紧耦合架构**
   - 4 个 UI 进程（Docker Desktop.exe） + 1-2 个 service 进程（com.docker.backend）
   - 杀任何一个 service 进程会导致 daemon 挂
   - 验证时一定要看 `Process.Path` 而不是凭 `ProcessName` 判断角色

4. **WSL2 是 Docker Desktop 的运行时**
   - docker-desktop distro 状态必须在 Running，否则 daemon 起不来
   - `wsl -d docker-desktop` 可手动启动 distro
   - 但 distro 起来不代表 daemon 起来（service 层可能还卡着）

5. **GitOps/集群恢复需要元数据 + 容器一致**
   - 删 daemon 不删 metadata（kind get clusters 仍可见）= 假死状态
   - 必须 `kind delete cluster` + `kind create cluster` 完整恢复
   - 或者 `kind export kubeconfig --name X` 后直接重建
